## (2) Verification of background item (Stanford/SLAC AI agent for beamline sample alignment, Nature Machine Intelligence, July 2026)

### Takeaway
The background item is CONFIRMED, with corrections: the paper exists and is peer-reviewed, but it is a proof of concept. On the real beamline, a human relayed every command (facility safety rule); the real-beamline trials were few and the authors state they "should not be interpreted as a statistically established capability"; no time comparison with a human operator is reported. The agent drove the beamline's existing control software (SPEC command set) through Model Context Protocol (MCP) tools using off-the-shelf Anthropic Claude models (Opus 4 on the real beamline; Sonnet 4 and Google Gemini 2.5 Flash benchmarked in simulation). No instrument vendor product, API or partnership is part of the method.

- Task performed: find the primary reference reflection (0,0,6), optimise intensity and centre it (η, χ, δ scans), find secondary reflection (1,0,10) including in-plane ϕ search, set or0/or1, determine the orientation (UB) matrix and refine lattice parameter c; verification on (2,0,14). The agent detected and reused an unexpected ~1.22° η offset (attributed to the uneven copper holder). — [OSTI PDF](https://www.osti.gov/pages/servlets/purl/3818105)
- Control interface: the agent issued SPEC-style terminal commands (wm, wh, umv, pd exposure, dscan, ca, or0, or1, setlat); SPEC is cited as "Certified scientific software SPEC—X-ray diffraction software" (ref. 71). Tools exposed via an MCP server the authors built; scan results returned as rendered plots with fitted curves, detector images as images (the agent does not see raw numeric arrays). "Minor environment-specific adjustments were made to MCP tools to match the real-beamline control interface." Bluesky/EPICS are not used as the agent interface in this paper. — [OSTI PDF](https://www.osti.gov/pages/servlets/purl/3818105)
- Safety arrangement: in the real experiment the agent output "Execute Command: [commands]" and a human experimentalist relayed it to the terminal "solely to satisfy facility safety requirements"; motor soft limits from BL17-2 were applied in simulation (e.g., δ −1.0° to 55.0°, χ 85° to 185°). — [OSTI PDF](https://www.osti.gov/pages/servlets/purl/3818105)
- Models: real beamline used Anthropic Claude Opus 4 (via Claude Desktop) "to maximize robustness and minimize operational risk"; simulation benchmark compared Claude Sonnet 4 (Claude Desktop and LibreChat API) and Google Gemini 2.5 Flash (LibreChat API); no fine-tuning ("the core reasoning model is used off the shelf"). — [OSTI PDF](https://www.osti.gov/pages/servlets/purl/3818105)

### Inferences
- The judge in this demo is exactly the thesis's "fast, unambiguous judge": Bragg-peak intensity/position on a known crystal. But the scored metrics (≤15° alignment tolerance; c within 0.01 Å) are loose relative to production crystallography; the result shows feasibility, not production readiness.
- Value capture signal: the agent sat on top of a generic, decades-old command language (SPEC) via an open protocol (MCP) using a general-purpose frontier model, with no vendor API. This favours the facility/user and the model supplier, not the instrument maker, at least at synchrotrons.
- The human relay shows that "cost of damaging hardware"/facility safety policy is the binding constraint at real beamlines today, not model capability.
